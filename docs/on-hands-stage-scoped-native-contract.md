## Two exact-candidate gates

FAST: each ordinary Java/UI/resource/test increment requires the exact candidate Java compile, all existing unit/host/voice/ad/locale/release-evidence regression steps, native-build-scope success and secure-relay-unit-test success. The expensive cooperative-apk job is intentionally SKIPPED only when the classifier proves an eligible ordinary development push; record APK/AAB/16 KiB as DEFERRED_TO_STAGE_CHECKPOINT (NOT_RUN for this candidate), never PASS. A successful aggregate workflow with a skipped packaging job is not Native acceptance. Do not advance on failed, missing or pending required FAST evidence. Prior known build failures must be resolved; do not hide failures through a later skip.

FULL: at the end of each major P3, P4, P5, P6, P7 and P8, and at final P9 freeze, update docs/on-hands-native-checkpoint.json in the last scoped candidate or a dedicated checkpoint commit. The checkpoint commit itself is the exact app candidate built and accepted by both workflows. Change the checkpoint contents (stage, reason, prior candidate, revision) so the change is observable. Manual workflow dispatch also always requires full packaging. Native-affecting changes (C/C++, JNI, native Java boundaries, native engine binaries/configuration/build tooling, packaging/dependencies) require FULL immediately, not at a later stage. If a Java file with ordinary name changes native invocation/routing/ABI or native integration semantics, the developer MUST add the checkpoint marker in the same commit; a path heuristic is not semantic analysis. Unknown paths, missing/non-ancestor commit ranges, non-development branch runs, manual dispatch, or classifier change require FULL. A new CI policy/bootstrap run is FULL once because packaging workflow/control changes are classified conservatively.

FULL requires exact Java/regressions, native-build-scope, secure relay checks, cooperative-apk, native payload, APK, QA AAB, ELF/APK 16 KiB audit and nonexpired matching artifact receipts; never advance a major-stage boundary or native-impact change before acceptance. If failed, repair and rebuild. Earlier APK/AAB artifacts may not be substituted for the final candidate. Existing final evidence collector remains strict and does not count skipped native as PASS.

## Workflow and governance

Both workflows still run on source/test/build/marker changes. secure-relay-unit-test is never disabled by this policy. Existing native build steps, signing lock, ad, permissions, five locales, native engines, original 22 release gates, score >=90 each and mean, real device testing at FINAL, actual independent review and separate release approval remain unchanged. The only change is packaging cadence. Keep A/B/C simulated KPI before each scoped implementation, source/test review, exact expected-head non-force commits, single branch, real gate evidence and repair-first. Do not use the deferred packaging rule to permit a known unresolved P0/P1 defect or claim unverified runtime support.

The classifier uses actual Git changed paths, no rename hiding, ancestry/commit validation and a conservative native-sensitive Java name rule. It runs pure Python standard library tests in Java CI. New unknown file classes or semantic engine changes need explicit FULL checkpoint. Only dev branch eligible; no main merge/release/production configuration change. Existing in-flight P3A1 native run is not cancelled or retroactively marked passed.
